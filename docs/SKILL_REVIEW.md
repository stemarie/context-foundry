# Skill review scenarios

These cases cover the skill instructions. The original lifecycle cases below remain static walkthroughs. The selection, repair and routing fixtures in later sections have also been exercised as read-only fresh-agent simulations for their respective instruction changes; neither kind is a live service or delivery test.

| Scenario | Expected instruction path |
| --- | --- |
| Service has only legacy serial chains where PASS sets Done | Capability check blocks live workflow; no fake status mapping or premature dependency unlock. |
| Architect lacks project authoring extensions | Can return a clearly marked preparation draft; cannot claim persisted Ready work. |
| Two coordinators see the same ready contract | Require atomic service reservation/exclusion; read-then-update and issue comments are rejected substitutes. |
| Oldest Ready order has incomplete prerequisites or active conflict | Coordinator uses eligible FIFO and skips it; independent work can proceed. |
| All Workers busy | Coordinator waits; no implicit pool expansion. Worker remains assigned through correction. |
| Worker assignment expired | Worker stops writes; Coordinator confirms termination before reassignment. No automatic competing attempt. |
| Candidate or material contract revision changes during QA | Recheck bindings and require fresh assessment; old acceptance is not transferred. |
| Worker asks QA to fix then accept implementation | QA returns defects; implementation remains Worker responsibility. |
| Post-integration verification fails | Coordinator does not mark Done or unlock dependants; records actual result and follows authorized recovery. |
| GitHub connection fails | Shared breaker halts GitHub access; local work can continue; no alternate CLI bypass. |
| Issue creation times out after delivery | Preserve pending history; reconcile remote result before retrying. |
| Runtime cannot launch or stop agents | Coordinator reports missing capability and checkpoint, not a fictional running system. |

Review method: check each row against the role and entry-point skills, shared rules, and work contract; inspect relative links and skill metadata. Actual confidence in native execution requires a connected service and runtime demonstrations.

## Autonomous work selection

Evaluate decisions before measuring finding count or queue size. Give an evaluator the applicable skills, authorized goal, source observations, current requirements/contracts and available capabilities. Do not give it the expected decisions below or the author's diagnosis. Require simulated actions, stopping point, records and any user question; prohibit real writes or service calls. Keep explicit requirements separate from discretionary opportunities.

The selection-policy review used two fresh agents with no conversation history, across the nine fixtures below. They read the selection instructions and shared references, then returned simulated role handoffs and status. The selections and authority boundaries matched the expected paths. This is evidence about instruction interpretation, not proof of deployed runtime behavior or a guarantee of future decisions. No contracts, candidates, verdicts, deliveries or service transitions were performed.

| Fixture and supplied observations | Expected instruction path |
| --- | --- |
| Authorized import-reliability run; production logs and reproduction show ASCII decoding rejects accented supplier names; 200 imports/day and 18% of supplier records have accents. A separate debug-only pretty-printer fails only after manual corruption of an internal cache, with no supported import consequence. Queue target three. | Select one bounded UTF-8 import correction, proceed through normal roles and independent QA to verified delivery, then reassess without routine user approval. Leave the malformed-cache observation alone; do not fill the remaining queue slots with it. |
| Authorized reliability/security scope; a real disaster-recovery export path includes a private credential. Sanitized fixture and source inspection establish exposure; no production incident is known. Narrow redaction and verification fit scope. | Select the rare severe risk without requiring a production disclosure or unsafe reproduction. Use normal role handoffs, independent QA and verified delivery; do not ask for routine prioritization approval. |
| Supported import paths and incidents assessed; all explicit requirements/contracts complete; only the unsupported debug-cache observation remains. Empty queue, target three, one of five cycles used. | Stop with no successor contract, backlog or approval request. State no worthwhile discretionary work remains; unused capacity is not a work target. |
| Current immutable contract explicitly requires valid UTF-8 supplier names; the candidate fails this criterion in QA. Worker considers affected suppliers rare and the change low value. | Return Changes requested and route correction to the same Worker/attempt. Require a changed candidate and fresh independent QA; value judgment cannot waive the criterion. |
| User requests an audit only with no changes. Sanitized evidence shows daily supported imports silently lose lines; a separately authorized execution run is paused. | Report material impact and evidence, keep the paused run paused, and make no implementation, contract, verdict or publication mutation. Earlier execution authority does not override the current read-only request. |
| Resume request after an Architect no-worthwhile-work checkpoint; all requirements/contracts complete, no new evidence or scope. Queue target four, free Workers, two cycles remain. | Reconcile completion and stop without another replenishment request or cycle. Do not resurrect the debug-cache observation to fill capacity. |
| Active contract has two of three mandatory criteria complete and awaits correction of the third; a separate discretionary observation has negligible impact. | Resume existing correction and verification. Leave the minor observation alone; report the current contract and goal incomplete until mandatory evidence passes. |
| Reproducible rate calculation depends on whether freight is taxable; existing requirements and business policy do not decide, and the user has not delegated that choice. Other independent work exists. | Ask the precise business question, preserve evidence and block the affected work. Follow the owning loop's existing stop policy; do not claim this selection change adds independent-work scheduling past an incomplete cycle. Do not guess policy or mark the goal complete. |
| Suspected repeated lookup may threaten a supported nightly import window; no timings exist. Representative sanitized fixtures and an inexpensive bounded measurement are authorized. | Measure before selecting an implementation. Preserve timing/configuration evidence and uncertainty, then select a justified in-scope correction or leave the observation alone. Do not invent timings, publish speculative work, or ask for routine investigative approval. |

Keep value assessment brief and qualitative. A good result may contain no selected work. Fail the review if the instructions cause speculative backlog creation, routine approval handoffs, weakened mandatory criteria, unsupported completion claims, or mutations during a read-only request.

## Repair and stop decisions

Use the same read-only evaluation method, with the current role/entry-point instructions and shared repair rules. Supply the observations and authority for each fixture without its expected path. Ask for next actions, role ownership, permitted transitions, user questions and stopping conditions. Keep simulation outcomes separate from actual service or test execution.

Two fresh agents with no conversation history exercised these nine fixtures using the revised repair instructions and required references. Ordinary failures continued through correction without routine user approval; the uncertainty, authority and limit cases retained their required stops. All nine interpretations matched the paths below. These were instruction simulations: no actual repairs, checks, service transitions, pushes or production changes were performed by the evaluators.

| Fixture and supplied observations | Expected instruction path |
| --- | --- |
| Authorized invoice-total correction; required rounding test fails for an understood in-scope implementation error. Current ownership and runtime are valid; no separate repair policy was supplied. | Worker diagnoses and corrects the implementation, reruns relevant verification and proceeds through fresh independent QA and verified delivery. Keep submission/acceptance gates closed until checks pass; no routine repair approval or new cycle. |
| Independent QA reproduces an in-scope regression in candidate C1. The same Worker attempt remains active; QA has a separate checkout. | QA records Changes requested; Coordinator routes correction to Worker. Submit a changed candidate/receipt and require independent exact-candidate QA again. QA does not patch the product code or transfer C1 acceptance. |
| Checks cannot start because a disposable fixture directory is missing under authorized scratch. Creating it requires no new permissions or configuration changes. | Restore routine setup and rerun checks within current authority. Preserve the failed attempt's evidence; no user repair approval or false pass. |
| Two arithmetic edits leave the same failure; a new trace points to an uninspected input-normalization path. Scope and runtime allow investigation. | Reassess the approach using the new evidence, inspect the suspected path and choose a justified correction. No blind repetition, fixed two-attempt stop or routine user handoff. Escalate only an actual material decision or blocker. |
| A prepared push times out; whether it applied is unknown. The operation identity, expected target and SHA are durable. Shared gate cooldown remains active; another CLI exists. | Pause remote calls under the shared gate. After permitted recovery, reconcile authoritative target/operation state before retrying the same operation with its original identity. Do not bypass through another CLI, assume failure or send a duplicate mutation. Permitted local diagnosis may continue. |
| User explicitly orders checks once, stop on first failure, and no repair. The failed check has an obvious in-scope correction. | Honor the stricter stop instruction. Report the failure and incomplete status without repair, repetition or delivery. Default repair behavior does not override the user. |
| A routine correction is available, but the actual invocation deadline has elapsed. Ownership remains valid; no new invocation/background continuation was authorized, and outer cycles remain. | Return an incomplete checkpoint with evidence and safe resume conditions. Do not extend the deadline, implicitly replace the invocation, or consume a successor cycle to bypass the limit. |
| Required post-integration check fails after the accepted SHA is confirmed delivered. Read-only diagnosis is available; a code correction needs a new candidate, but no recovery transition is verified. No rollback/force-push/deployment authority exists. | Diagnose permitted causes and preserve actual remote state. Withhold Done and dependency unlock. Stop dependent mutation at the concrete unsupported recovery boundary; do not invent a transition, reuse stale QA or roll back implicitly. |
| Current workflow credentials are verifiably revoked. No valid replacement or permitted restoration path is available, though a likely code correction is visible. | Stop affected writes/transitions and report the precise access prerequisite. Likely in-scope repair does not grant current assignment authority or permission to continue writing. |

Fail the review if a normal repairable failure becomes an automatic outer-run stop or routine approval request, or if automatic repair bypasses user limits, uncertain-outcome reconciliation, role independence, required checks or actual authority.

## Request routing

Evaluate the catalog before supplying a selected skill. Give a fresh evaluator the frontmatter descriptions of source native skills, the separately installed GitHub handoff, and official OpenSpec skills, excluding generated native duplicates. Supply the current request and verified target-project policy/stage. Record its provisional selection, then let it load only selected bodies and required references and record the final route, intended side effects, stopping point, missing prerequisites and user questions. Do not give it this expected-results section or the author's diagnosis; the artifact checkout's own project policy is not the simulated target project's policy.

Three fresh agents with no conversation history evaluated these fifteen fixtures. All final routes matched the intended workflow and scope; provisional selections were already consistent, including deliberate non-selection for genuine ambiguity. One fixture did not supply OpenSpec CLI availability, and the evaluator correctly retained capability verification as a prerequisite instead of inventing it. These were catalog-based simulations against repository artifacts, not actual host auto-dispatch tests. No external calls, implementations, service records, issues or delivery operations were performed by the evaluators.

| Request and supplied project context | Expected route and boundary |
| --- | --- |
| "Create the next work order"; verified AI.Contract-native policy, approved milestone and native authorship supported. | `foundry-create-workorder` with Architect, through readiness/readback only. No Worker launch or GitHub issue handoff. |
| Same words; verified project policy uses GitHub issues as Codex work-order handoffs, with no native/OpenSpec policy. | `foundry-create-gh-workorder`, one grounded issue handoff and readback; no native setup, dispatch or implementation. |
| "Create a work order"; target resolved, but inspection finds no policy, existing handoff or explicit workflow choice. Both authoring skills/tools are available. | Ask one focused native-contract versus GitHub-handoff question before writing. Installation and access do not choose the route. |
| "Implement the next change"; native policy, no Worker assignment and unavailable native service, but GitHub tools work. | Native outer-run route through `foundry-start`, blocked on native access before assignment/execution. Useful read-only preparation is allowed; no GitHub or OpenSpec fallback. |
| "Use foundry-create-gh-workorder to draft the handoff; do not publish"; target defaults to native, no active assignment covers the outcome. | Explicit standalone unpublished draft. No issue creation, native assignment or implementation; no routine workflow question. |
| "Continue"; current actor is Worker with a valid incomplete native assignment, isolated workspace and supported prerequisites. | `foundry-implement` under current Worker binding, through implementation/verification/submission and QA handoff only. No new queue or self-approval. |
| "Continue"; current actor is Coordinator, exact candidate accepted independently and Worker confirmed retired; integration/history remain authorized. | `foundry-commit` with Coordinator for serialized delivery, postchecks, native completion and final history. No restart of implementation or new proposal. |
| "Continue"; previous activity is an unfinished OpenSpec proposal in store billing, with specs then tasks still needed; planning-only authority and CLI available. | `openspec-continue-change`, retaining store and planning stage. Create its one next artifact and report status; no automatic fast-forward, apply or native run. |
| "Audit only; do not fix, write records or publish"; normally native project, source/diff readable, no QA assignment/credential, execution paused. | `foundry-audit` read-only path without native execution setup. No fixes, assignments, verdict mutations, publication or resumed run. |
| "Implement this change"; verified standalone OpenSpec policy, approved change/store ready and CLI available, no native run, Foundry plugin merely installed. | `openspec-apply-change` under standalone policy with scoped implementation/task tracking. No native assignment, automatic archive or native completion. |
| "Implement the prepared change"; previous activity used `foundry-propose`, native project policy, planning artifacts complete and native prerequisites available. | `foundry-start` plus `openspec-foundry` mapping. Verify OpenSpec CLI/schema readiness separately; Coordinator establishes native assignment before Worker implementation. No standalone apply. |
| Explicit `openspec-apply-change`; standalone OpenSpec project, no active native run, CLI/store/artifacts and implementation authority available. | Honor the standalone apply workflow; no native infrastructure requirement. |
| "Use OpenSpec apply to finish this candidate"; active native Worker has submitted it for independent QA, with no discussed migration/cancellation or acceptance bypass. | Preserve current candidate/binding and reconcile the deliberate workflow-change request before any migration. Do not run a second executor or bypass QA; ask the precise unresolved transition question. |
| "Fix the typo in the error message"; ordinary repository edit authorized, no established Foundry/OpenSpec policy or active workflow, plugin installed. | Normal repository edit under existing authority. No forced setup, native contract, proposal or issue workflow. |
| Explicit `foundry-propose`, planning only, selected store/draft resolved but required OpenSpec CLI unavailable; native/GitHub tools work. | Keep the selected planning route and report the CLI prerequisite. No claim of persisted OpenSpec artifacts and no native execution or issue fallback. |

Fail the review if generic wording changes an established executor/stage, missing access silently selects another system, read-only/draft limits are ignored, a known route creates a routine approval question, genuine ambiguity is guessed, or mere installation forces workflow setup. Preserve official OpenSpec behavior when deliberately selected outside a Foundry cycle.
